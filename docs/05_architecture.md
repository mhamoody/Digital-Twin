# 05 — Architecture

## Target data schema

This is the yardstick every candidate dataset is measured against — built out from the supervisor's example fields (Student, Login Activity, Clickstream, Questions, Assessment, Score), extended with fields the literature review and the proposal's four objectives require. This schema is a deliverable in its own right, not just a design note.

| Field | Description | Expected source | Status |
|---|---|---|---|
| `student_id` | Anonymized unique student identifier | OULAD (`id_student`) / sandbox student table | Confirmed available (OULAD) |
| `demographics` | Age band, gender, disability, prior education, region | OULAD `studentInfo` | Confirmed available (OULAD) — not present in Stanford MOOCPosts |
| `module_presentation` | Which course offering/term a student is enrolled in | OULAD `studentRegistration` / sandbox course table | Confirmed available (OULAD) |
| `login_activity` | Timestamped record of VLE/LMS logins | OULAD `studentVle` (aggregated daily, not per-event) | **Gap — granularity mismatch.** OULAD gives daily click *sums* per material, not individual login timestamps. Handling decision: approximate — treat daily aggregated click counts as a login-activity proxy; do not fabricate individual login timestamps that don't exist in the source data |
| `clickstream` | Per-material interaction counts over time (VLE page/resource clicks) | OULAD `studentVle` + `vle` | Confirmed available (OULAD) — this is OULAD's core strength |
| `forum_posts` | Free-text student posts, with thread/context | Stanford MOOCPosts | **Gap — population mismatch.** MOOCPosts posts come from 11 different, non-credit Stanford MOOCs, not from the pilot course or from OULAD's students. Handling decision: simulate — seed the sandbox's forum layer with posts constructed to match MOOCPosts' confusion/urgency/sentiment *distribution*, not its literal text (see `03_solution.md` for the full reasoning; this is a deliberate, justified simulation, not a default) |
| `forum_labels` (confusion, urgency, sentiment, question/answer/opinion flags) | Human-coded Likert (1–7) and categorical labels on forum posts | Stanford MOOCPosts (`confusion`, `urgency`, `sentiment`, `question`, `answer`, `opinion` dimensions) | Confirmed available (MOOCPosts) for the *synthetic* forum layer's target distribution; not available for any *real* course's own posts, which is exactly why the LLM classification layer is needed rather than reusing MOOCPosts labels directly on the pilot course |
| `assessment_type` | Assignment/exam identifiers, weight, due date | OULAD `assessments` | Confirmed available (OULAD) |
| `assessment_score` | Per-student, per-assessment score | OULAD `studentAssessment` | Confirmed available (OULAD) |
| `final_result` | Pass / fail / withdrawn / distinction outcome | OULAD `studentInfo.final_result` | Confirmed available (OULAD) — this is the label the at-risk classifier is validated against in `02.7` |
| `time_window` | The week/period a given engagement or grade record belongs to | Derived from OULAD's `date` fields relative to module start, or sandbox timestamps | Confirmed available (derivable) |
| `at_risk_flag` (system output, not source data) | The model's own prediction, stored alongside the ground truth it's evaluated against | N/A — generated by the classifier described in `05` below | Not a source field — explicitly generated, never fabricated as if it were observed data |
| `llm_explanation` (system output, not source data) | The one-sentence gap explanation generated per flagged post | N/A — generated by the LLM analytics layer | Not a source field — explicitly generated |

**Fields considered and explicitly excluded (not silently dropped):** video/audio interaction data (excluded per the proposal's own scope — textual and structured engagement data only) and any Queen's-specific institutional field (excluded per Meeting 2's constraint on internal data use at this stage).

## Data flow, described in build order

1. The Moodle sandbox is seeded once (see below) with synthetic structured and forum data whose statistical shape matches OULAD and MOOCPosts respectively, linked per student inside the sandbox.
2. A scheduled sync job calls Moodle's REST web services API to pull new/changed activity — logins/clicks, assessment submissions and scores, forum posts — since the last sync.
3. The sync job writes this activity into the digital twin database, keyed by `student_id` and `time_window`, following the schema above.
4. On a schedule (e.g., weekly, matching how an instructor would realistically review the dashboard), the structured classifier reads the latest engagement + grade features per student and produces an `at_risk_flag` probability.
5. On the same or a finer schedule, the LLM analytics layer reads new forum posts and short answers and produces `confusion`, `urgency`, and `llm_explanation` outputs per post, plus an aggregated per-student/per-topic summary.
6. The dashboard queries the twin database plus both analytics outputs and renders per-student trend lines, a ranked at-risk list, and the AI-generated recommendation text tied to specific evidence (flagged posts, engagement drop-offs).
7. The instructor reviews the dashboard and decides on any action; nothing downstream of step 6 is automated.

## Where synthetic data injection happens, tied to the concrete per-gap decisions

Per the schema table above, synthetic injection happens at exactly two points, both explicitly justified rather than defaulted to:
- **The forum-post text itself** (gap: population mismatch between OULAD's students and MOOCPosts' posters) — synthetic posts are generated to match MOOCPosts' *labeled-dimension distribution*, because the actual research goal (classifying confusion/urgency/generating explanations) depends on having text with a realistic *distribution* of those properties, not on any individual post being "real." This is explicitly not appropriate for fields where the individual value matters for correctness (e.g., a student's actual assessment score, which is never simulated — it comes straight from OULAD).
- **Login-activity granularity** (gap: OULAD gives daily aggregates, not individual timestamps) — handled by approximation (treating the daily aggregate as the login-activity proxy), not simulation. No individual login timestamp is invented.

No other field in the schema is filled by simulation. Demographics, assessment scores, clickstream counts, and final results all come directly from OULAD with no synthetic substitution, because misrepresenting those specific fields would directly undermine the honesty of the at-risk classifier's evaluation in `02.7` and `02_goal.md`'s "done" definition.
